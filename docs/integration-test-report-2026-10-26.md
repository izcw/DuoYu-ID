# 多鱼账号：多项目接入测试与升级方案

测试日期：2026-10-26。对象为当前本地代码与 localhost:8080 服务。本次新增协议与浏览器测试，未修改生产认证逻辑；下面的改进项是待实施方案，不表示已经修复。

后续修复与当前状态见 [2026-10-27 升级交付记录](session-upgrade-2026-10-27.md)。本文保留修复前测试事实。

## 1. 结论

现有版本已经能支撑自有网站的统一认证：机密客户端、公共客户端和纯浏览器 SPA 均完成了真实跳转、登录、授权码兑换、签名验证和 UserInfo 获取。同一账号在不同项目取得一致的用户标识，项目应以 `iss + sub` 建立本地用户。

适合先接入少量自有 Web 项目试用，不宜直接宣称完整的企业身份平台或所有客户端均已支持。最优先处理多标签页登录冲突、中心与项目的会话失效规则，以及正式域名上的真实设备验收。

“中心完成登录”与“项目继续接受自己的 Cookie”是两层状态。中心不能直接删除另一站点的 Cookie，也不能自动改变项目数据库；全局退出、停权传播等能力必须由中心与接入项目共同实现。

## 2. 测试方法与结果

### 2.1 实际启动三个接入项目

使用两个独立 Go 示例进程及一个临时 SPA HTTP 服务，各自注册不同 client_id 和回调地址，浏览器完成完整流程。所有账号、项目和验证码为一次性测试数据；验证码直接写入开发数据库，并拦截发信接口，没有调用真实 SMTP。

### 2.2 Go 协议与异常路径

新增 `server/client_matrix_test.go`，接入原有 TestIntegration，使用随机 PostgreSQL schema。新增矩阵包含 22 个子测试，全部通过。这里“通过”也包括确认某个限制确实存在，不能解释成 22 项功能都完整支持。

- 复现同浏览器多个标签页的流程 Cookie 覆盖；旧标签页请求失败。
- 验证 prompt=login、max_age=0 的重新认证边界，以及 prompt=none 当前返回 login_required。

### 2.4 覆盖边界

三个项目使用不同 localhost 端口：已验证不同 origin，但仍属于同一 site，不能代替不同正式域名、跨站 Cookie 策略的验收。扫码使用独立浏览器上下文和虚拟认证器，不能证明真实 iPhone/Safari、iCloud 同步、Face ID 或系统跨设备通行密钥体验。

本轮没有测试真实邮件送达、互联网 HTTPS 部署、真实硬件、生产并发容量、所有第三方 SDK、完整 OIDC 一致性认证，亦未穷尽 introspection/revocation/RP-initiated logout 的所有组合。结果不是完整安全审计。邮件队列测试使用模拟传输，SMTP 接受也不能描述为用户收到邮件。

## 3. 应当如何接入

| 项目类型 | 推荐方式 | 项目需要负责 |
| --- | --- | --- |
| 有后端的网站 | OIDC Authorization Code + S256 PKCE，机密客户端，后端兑换 | 服务端保管密钥、校验 state/nonce/令牌、建立安全 Cookie 会话 |
| SPA，有可用后端 | 优先通过自己的后端完成认证与会话管理 | 浏览器只持有会话 Cookie，令牌留在后端 |
| 纯静态 SPA | 公共客户端 + S256 PKCE，使用成熟 OIDC 客户端库 | 不放 client_secret；严格回调与令牌验证、XSS 防护、明确刷新后登录策略 |
| 桌面/移动 App | 暂不作为已完整支持的产品能力；补齐原生客户端后用系统浏览器 + PKCE | 外部浏览器授权、合规回调、系统安全存储 |
| 项目自己的账号密码表单 | 当前不能直接跨源提交中心认证接口 | 先用跳转；确需无跳转时，单独设计受信项目的验证码认证能力 |
| 后台任务发邮件 | 项目 API 凭证，授予 mail:send，按需 mail:read | 服务端存储凭证、幂等键、处理排队/失败状态；不能把 API 凭证当用户登录令牌 |

建议提供 Go、Node.js 和 PHP 的小型接入示例与一致的验收清单。减少适配的关键是固定标准协议和返回字段，不是让项目绕过身份校验。头像和昵称可缓存，但不能用邮箱作为不可变用户主键。

## 4. 缺点与改进设计

### P0：正式扩大接入前完成

**多标签页流程互相覆盖（已复现）。** 当前单一 duoyu_flow Cookie 被后打开的登录流程覆盖，旧标签页完成时被拒绝。改为同一浏览器绑定下可并存的多个短期授权流程，每个流程有随机标识、独立一次性状态、到期时间和数量上限；不能为解决冲突而去掉浏览器归属校验。验收：同浏览器 A/B 两页任意顺序完成均成功，跨浏览器冒用、重放、过期仍失败。

**中心与项目会话失效不联动（已复现）。** 第一阶段明确项目会话最长有效期，敏感操作进行在线状态复核；第二阶段增加标准 OIDC Back-Channel Logout，并为停权/准入撤销定义清晰的失效事件。项目按 sid/sub 删除自己的服务端会话，事件验签、检查受众和事件类型、去重，中心持久投递并重试；不能在事件中放密码、验证码和业务数据。离线项目恢复后需补偿同步。建议先约定在线项目失效传播目标 ≤60 秒，作为验收目标而非当前承诺。[标准依据](https://openid.net/specs/openid-connect-backchannel-1_0.html)。

**正式域名与真实设备验收（尚未覆盖）。** 固定 issuer 与 WebAuthn RP ID，配置 HTTPS、可信代理、精确回调；在两个不同正式站点完成登录与退出。实机测试 iPhone Safari 的密钥注册、扫码确认、取消、过期及账号恢复。当前“苹果扫码”是多鱼自己的二维码确认流程，并非 Sign in with Apple；应使用不会混淆这两种能力的说明。

### P1：稳定接入体验与运维

**重新认证体验。** prompt=login/max_age=0 应进入明确的重新验证流程，而不是要求用户先退出整个账号。保留授权请求、绑定重新认证时间；验证完成后续接原回调。避免用普通已有会话满足强制重新认证。

**会话续期缺失。** 当前令牌寿命 5 分钟，没有 refresh token，prompt=none 也不支持静默续期。短期网站可用受控本地会话加交互式登录；需要长时间在线的客户端再增加刷新令牌轮换、令牌家族、重用检测、逐设备撤销与绝对有效期。公共客户端刷新令牌需使用发送方约束或轮换等保护；不能简单生成一个长期不变的 token。[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)。

**接入配置表达不够准确。** 将“机密/公共”与“Web/SPA/原生”分开建模，分别显示密钥要求、回调规则、退出方式及支持范围。增加配置检查页：issuer、Discovery、回调、PKCE、scope、最近失败原因和脱敏请求编号；不能在管理面板展示授权码和完整令牌。

**原生应用回调尚未支持。** 按需实现桌面 loopback IP/动态端口、受验证的 HTTPS App Link 或经过严格限制的私有 scheme，逐类校验；不能通过放宽所有 redirect_uri 解决。采用系统浏览器而非内嵌 WebView 收集统一密码。[RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252)。

**管理查询和审计。** 最近 200 条列表改为服务端分页和筛选，覆盖用户、项目用户、邮件与审计；保留稳定排序。加入 request_id、client_id、错误分类及登录方式，打通一次授权的排障路径；敏感信息脱敏。账号管理增加会话列表和逐设备撤销。

**永久凭证与管理分权。** 保留永久有效选项，增加最近使用时间/IP、权限范围、轮换窗口和异常使用提醒；设计系统管理员、项目维护者、审计只读角色，服务端强制授权。永久不等于不可撤销，也不应默认授予全部权限。

**维护与监控。** 已有加密持久邮件队列、编号迁移、备份/隔离恢复脚本、可信代理与未知账号 dummy 密码校验，不需要重复建设。下一步定时备份和恢复演练，监控登录错误率、认证延迟、队列积压、SMTP 不确定状态、数据库容量；定义各表保留期和分批清理。配置签名密钥平滑轮换及新旧 JWKS 共存。

**邮件可靠性。** 保留默认文字模板和项目自定义 HTML，不增加后台模板编辑器。提供清晰的排队/发送接受/失败/不确定状态查询；评估独立事务邮件服务和签名回执。真实 QQ SMTP 投递需另行人工验收；不能因超时盲目重发产生重复验证码或告警。

### P2：规模增长后按需建设

- 统一 OpenAPI/DTO 类型、提取重复表单和错误处理；CI 自动运行协议矩阵、页面测试与构建。
- 构建产物中存在约 1.33 MB 的 JS 块（gzip 约 442 KB）：用依赖分析确定内容后按路由懒加载、拆分图表和非必要编辑器资源；未做性能测试，不能据此直接断言页面卡顿。
- 明确第一方受信项目与第三方项目的授权策略。第三方接入再增加授权记录、可撤销授权与隐私范围说明，避免给所有场景强加注册勾选框。
- 若确需项目内登录，先限制到受信项目的邮箱验证码流程：挑战绑定项目/邮箱/用途、一次性消费、限流与准入；不要新增任意第三方可用的统一密码换 token 接口。
- 暂不引入租户隔离、业务角色托管、业务数据库托管或文件托管，保持多鱼的范围为身份认证、账号管理和公共项目邮件。

## 5. 推荐实施顺序与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| 第一阶段：登录可靠性 | 多标签页修复、重新认证界面、客户端类型说明、接入排障页 | 双标签任意顺序完成；旧授权不串用；异常路径回归全过 |
| 第二阶段：会话闭环 | 会话列表、撤销策略、全局退出事件及接入示例 | 项目本地退出与全局退出明确区分；事件验签/重复/乱序/离线补偿通过；达到约定传播时限 |
| 第三阶段：正式验收 | 双域名 HTTPS、真实 iPhone、邮件投递、备份恢复、监控与容量基线 | 有可复核记录；密钥/数据可恢复；无敏感日志；容量目标按实际业务确定 |
| 第四阶段：按需扩展 | 刷新令牌、静默认证、原生客户端、细粒度后台权限 | 每项有协议说明、攻击/异常路径测试、兼容性与迁移文档后再开放 |

不要同时扩大所有能力。若近期只接自有 Web 网站，先完成前三阶段；原生客户端、嵌入式登录与长会话不是必选项。

## 6. 兼容与后续验收清单

保留现有 client_id、issuer 和 sub，新增配置默认维持已有客户端行为。数据库使用编号迁移；新增事件接入和刷新能力逐项目启用。中心页面、头像展示、邮件模板改动一般不要求项目修改；全局退出和新的接入能力要求项目一次性增加对应处理，这一成本不能消除。

正式发布还需覆盖：不同站点的 Chrome/Firefox/Safari；真实 iPhone；关闭/拒绝浏览器权限；扫码过期/重复确认；并行登录和取消；网络断开及超时；令牌过期；禁用用户/项目/准入；退出事件延迟/重放；密钥轮换；多实例与邮件 worker 重启；数据库恢复；持续负载及密码哈希资源上限。

## 7. 复现入口

需开发 PostgreSQL 和本地服务已启动，Go、Node、Chrome 可用。不要在生产数据库运行浏览器夹具。

```powershell
$env:DUOYU_TEST_DATABASE_URL='postgres://duoyu:duoyu_dev_only@localhost:55432/duoyu?sslmode=disable'
go test -count=1 -v ./server
go vet ./server
go build -o test-results/oidc-client.exe ./examples/client
pnpm --dir admin build
cd admin
node tests/multi-project.mjs
$env:SKIP_MAIL='true'
Remove-Item Env:TEST_PASSKEY -ErrorAction SilentlyContinue
node tests/smoke.mjs
node tests/session.mjs
node tests/admin-pages.mjs
```

协议测试使用并删除隔离 schema；多项目浏览器夹具创建后清理一次性账号、项目和进程。测试产物存放在已忽略的 test-results，不应提交数据库凭据、邮件授权码、Cookie 或令牌。
