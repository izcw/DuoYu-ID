## 当前能力与限制

已具备 OIDC 授权码 + PKCE、邮箱自动注册、密码登录、通行密钥与扫码确认、项目准入、永久可撤销 API 凭证、独立编辑页面、基础统计。此次新增项目邮件默认模板/自定义 HTML、独立权限、发送元数据与幂等记录，详见 [project-mail.md](project-mail.md)。

| 优先级 | 代码中的现状/缺点 | 下一步方案 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 中心邮件与项目邮件共享同步 SMTP，网络慢会占用 HTTP 请求；没有重试与回执 | PostgreSQL 持久队列 + 独立 worker，预留认证邮件容量；先用 PostgreSQL，规模需要时再引入专门消息队列 | 重启不丢任务，过期验证码不发送，明确区分接受/失败/不确定；模拟断网和进程中断 |
| P0 | QQ SMTP 共享账号是单一故障点，真实收件质量无法从代码证明 | 在正式域名完成真实投递验收；为消息发送封装可替换供应商，未来配置独立事务邮件通道及回执 | 验证收件箱/垃圾箱、拒收、超时；回执签名和幂等处理；不宣称 SMTP accepted=送达 |
| P0 | schema.sql 以幂等建表及 ALTER 初始化，没有迁移版本/回滚策略 | 引入编号迁移、上线前备份和恢复演练；明确单实例迁移执行者 | 新安装与已有数据库升级均可重复验收，失败可恢复，不在启动中无审查变更结构 |
| P0 | 中心停权不自动结束项目自己的会话 | 先定义接入方会话有效期和敏感操作复核；后续实现签名事件/back-channel logout，客户端按事件失效会话 | 验证用户停用、权限撤销及密码变更传播；明确传播时限和离线项目策略 |
| P0 | 代理后 IP 限流依赖连接 IP，所有用户可能共用限额 | 可信代理 CIDR 白名单、正确读取代理链，入口网关限流；不能直接信任任意 X-Forwarded-For | 真实客户端可区分，伪造转发头不能绕过限流 |
| P1 | 管理端仅管理员/普通用户两级，永久凭证泄漏风险随存续时间增长 | 审计只读、项目维护、系统管理员分权；永久凭证保留，增加最近使用 IP、异常调用提示、可重叠轮换 | 服务端强制范围限制，旧凭证可撤销，轮换无需瞬时中断 |
| P1 | 列表只取最近 200 条，前端分页/搜索不能覆盖历史 | 服务端游标分页、日期/项目/状态筛选，按查询补复合索引 | 超过 200 条仍能准确查询，导出只包含授权字段 |
| P1 | 过期会话、授权请求、令牌、限流记录、日志和旧头像没有统一清理 | 按表定义保留期，分批清理；邮件幂等保留期与元数据分开设计 | 清理可监控、无长锁；不能因清理导致旧邮件重复发送 |
| P1 | 签名 key 单文件固定，无平滑轮换 | 新旧签名 key 共存的 JWKS，切换签名并等待旧 token 到期后退休；备份密钥 | 轮换前 token 仍可按承诺寿命验证，新 token 使用新 kid |
| P1 | 缺少体系化监控与恢复演练 | 请求 ID、结构化错误分类、邮件延迟/失败率、数据库容量告警、自动备份及恢复脚本 | 日志不含密码、OTP、token、邮件正文；能定位接口失败并恢复到约定恢复点 |
| P1 | 登录错误提示统一，但不存在账号会快速跳过密码摘要校验 | 使用固定 dummy Argon2id 哈希校验未知账号，配合并发预算和限流 | 不以明显的计算路径差异暴露邮箱是否存在；压力下资源可控 |
| P2 | 多个前端页面使用 any，复用页面按 URL 分支，接口结构容易漂移 | 统一 DTO/OpenAPI 生成类型，拆分项目、凭证与准入表单组件，统一错误/空态组件 | 接口变更有编译检查，页面行为测试覆盖直接链接/刷新/离开保护 |
| P2 | 没有 refresh token、silent auth、完整单点退出，也未通过 OIDC conformance | 按实际客户端需求逐项补齐：轮换 refresh token 与重放检测、prompt=none、会话事件 | 每项先写协议边界及安全测试，再承诺标准兼容，不一次铺开 |

## 项目内登录的边界

现有版本仍使用 OIDC 跳转。若需要自有项目内嵌表单，后续独立实现“项目级邮箱验证码认证”：项目认证、挑战绑定 client_id/用途、尝试次数、有效期、一次性消费和用户准入校验。不要把此次业务邮件发送接口当作登录接口，也不要向任意第三方项目开放统一密码换令牌。内嵌登录不自动共享跨域 Cookie，通行密钥仍需按 RP ID/Origin 设计。

## 建议推进顺序

1. 本次：完成项目邮件发送及管理记录、权限隔离、幂等、默认模板与 HTML 支持；所有测试使用伪造传输，不触发真实邮箱。
2. 生产准备：版本化迁移、备份恢复、可信代理、独立邮件 worker 与优先队列、正式 HTTPS 和真实硬件/投递验收。
3. 使用规模扩大：服务端分页、日志保留、细粒度管理角色、凭证轮换和监控。
4. 按需升级：项目内验证码登录、全局退出事件、refresh token、供应商回执。不要为了“平台化”提前引入微服务、Redis 或多套数据库。

每阶段完成后更新文档和测试。标准接入协议保持稳定；破坏性接口调整采用版本路径及明确废弃期，不能保证所有未来改动都永远零适配。
